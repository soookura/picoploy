# picoploy 開発計画

## コンセプト

**ブラウザにフォルダをドロップすると、すぐに共有URLが発行される静的サイトのホスティングサービス**（Netlify Drop のようなもの）。

想定ユースケース：HTML + CSS 程度のサイトを、短時間だけチームメンバーに共有したい。

将来的には、ソースからのビルドやサーバーアプリにも対応したミニPaaSへ段階的に広げていく。

## この開発の目的

休日の個人開発として、Backend・DB・AWS・コンテナ・Kubernetes・ネットワーク・セキュリティ・CI/CD を実践的に学ぶ。

ただし **「技術を使うためにサービスを作る」のではなく、「サービス上の必要性から技術を使う」** ことを原則とする。

## 原則

- **モジュラーモノリスで始める。** プロセスを分けるのは、明確な理由（重い処理の分離、隔離など）が出たときだけ。
- **技術は必要になったフェーズで導入する。** 最初から全部入れない。
- **ローカルでできることはローカルで済ませる。** AWS は必要なときに立てて、終わったら壊す（Terraform で apply / destroy）。
- **設計判断は ADR に残す。** 「なぜそうしたか」を後から説明できるようにする。
- **期限は決めない。** フェーズの順番だけ決め、進めながら見直す。

## MVP（最初のリリース）の仕様

| 項目 | 決定 |
|---|---|
| 公開範囲 | 合言葉による限定公開。悪用対策が揃ったら一般公開する（[ADR-0002](adr/0002-passphrase-gated-launch.md)） |
| 合言葉の検証 | サーバー側で検証し、セッション（Cookie）を発行する。アップロード API はセッションがある場合のみ受け付ける |
| 合言葉が必要な範囲 | アップロード画面のみ。共有 URL は誰でも閲覧できる |
| ログイン | なし（匿名ドロップのみ）。ログインと Claim はフェーズ4 |
| 入力 | フォルダのドラッグ＆ドロップ。zip はフェーズ5 |
| 有効期限 | 1時間（設定値で変更可能） |
| 容量制限 | 合計 10MB・100ファイルまで（仮の値。設定値で変更可能） |
| ドメイン | 本体とユーザーサイトは別ドメインで配信する方針。ローカルでは `*.localhost` を使い、ドメインはフェーズ2で購入する |

### 基本的な流れ

1. 合言葉を入力してアップロード画面に入る
2. フォルダをドラッグ＆ドロップする
3. ブラウザがファイル一覧を取得し、API から署名付き URL を受け取ってストレージへ直接アップロードする
4. アップロード完了を API に通知すると、サイトが公開され URL が返る（例：`https://<slug>.<サイト用ドメイン>`）
5. 1時間後、期限切れのサイトは自動で削除される

## 技術スタック

| 分野 | 選定 | 理由 |
|---|---|---|
| 言語 | TypeScript | 普段の経験を活かし、フロントからバックまで統一する |
| フロントエンド | Vite + React（SPA） | [ADR-0003](adr/0003-frontend-vite-spa.md) |
| API | Hono + Node.js | Web 標準ベースで軽量。Node.js は本番運用の定番 |
| DB | PostgreSQL | |
| ORM | Drizzle | [ADR-0004](adr/0004-orm-drizzle.md) |
| 構成 | モノレポ（pnpm workspaces） | API とフロントで型を共有する（Hono RPC） |
| ローカル開発 | docker compose（PostgreSQL、Redis、MinIO） | |

## フェーズ

### フェーズ0：準備

- リポジトリ、計画、ADR
- AWS アカウントの準備と請求アラート（AWS Budgets）の設定
- 予算と常時稼働構成の検討（下記「未決定事項」）

### フェーズ1：MVP（ローカル）

- モノレポの雛形、docker compose
- 合言葉による認証（サーバー側検証 + セッション）
- フォルダのドラッグ＆ドロップと、署名付き URL によるアップロード（MinIO）
- サイトの作成と URL 発行、サブドメインでの振り分け（`<slug>.localhost`）
- 有効期限切れサイトの自動削除
- 容量・ファイル数の制限

学べること：API 設計、バリデーション、エラーハンドリング、PostgreSQL、Drizzle、マイグレーション、オブジェクトストレージ

### フェーズ2：AWS にデプロイ（限定公開）

- S3、CloudFront、Route 53、ACM（ワイルドカード証明書）
- VPC、IAM（最小権限）、Secrets Manager
- API のデプロイ（構成は予算と合わせて決める）
- Terraform による IaC
- GitHub Actions による CI/CD
- 本番でのマイグレーション運用

学べること：AWS、ネットワーク、IaC、CI/CD

### フェーズ3：一般公開の準備

- ユーザーサイトを本体と別ドメインで配信する
- レート制限（Redis）、AWS WAF
- ファイル種別の制限（HTML、CSS、JS、画像、フォントなどのみ許可）
- 一時公開サイトであることを示す表示
- 通報フォームと即時削除

学べること：セキュリティ、悪用対策、Redis

### フェーズ4：ログインと Claim

- GitHub ログイン（OAuth）
- 匿名ドロップしたサイトを、ログインして自分のものにする（Claim）
- サイトの永続化
- アトミックデプロイとロールバック（デプロイごとに新しい版を丸ごと配置し、本番が指す版を切り替える）

学べること：認証・認可、セッション、ブルーグリーン的な切り替え

### フェーズ5：zip とビルド

- zip のアップロード（zip 爆弾、パストラバーサルへの対策）
- Vite / React などのソースプロジェクトのビルド
- ビルドはキュー（SQS）に入れ、Worker が隔離された環境（Fargate）で処理する

学べること：非同期処理、Queue / Worker、コンテナ

### フェーズ6：サーバーアプリ

- コンテナで動くアプリのデプロイ（自分と招待した人のみ）
- ECS、Kubernetes（ローカルの k3d → EKS）
- マイクロサービス化の検討

学べること：コンテナオーケストレーション、ECS と EKS の比較、分散システム

## 予算の方針

- インフラの設計・構築と、実際のデプロイは必ず経験する
- 無料でできること（Docker、PostgreSQL、Redis、MinIO、k3d、Terraform の plan など）はローカルで済ませる
- AWS は必要なときに立てて、終わったら壊す
- AWS Budgets で請求アラートを最初に設定する
- 具体的な金額と常時稼働構成は別途検討する
